1  Project summary
What we are building, in one page
One line
One model imagines the document we are looking for; a second model decides how relevant each retrieved
candidate actually is — and we measure what each stage is worth separately.
A search query is three words. A relevant document is a two-hundred-word scientific abstract. They do
not look alike, which is why matching them directly is hard. And once candidates are retrieved, a BM25
score or a cosine similarity has never actually read the document — it has scored word overlap or vector
proximity.
We attack both ends. Stage A asks Qwen3 to write a hypothetical abstract that would answer the topic,
embeds that instead of the bare query, and retrieves the top 100 candidates. Stage B passes each
candidate to Clef — a decision model that returns a calibrated probability rather than text — and re-sorts
by P(relevant).
Pipeline
CORPUS (171,332 docs)                      TOPIC (50 queries)
      |                                           |
      | stage 1: encode once                      | stage 2: generate
      v                                           v
  FAISS index  <------------------------  hypothetical abstract (Qwen3)
      |                                           |
      |                 stage 3: embed + average + search
      v
  TOP-100 CANDIDATES  (frozen to disk — identical for every re-ranker)
      |
      | stage 4: for each candidate, ask Clef "is this relevant?"  ->  P in [0,1]
      v
  RE-RANKED LIST  --->  stage 5: evaluate vs TREC qrels  (nDCG@10, MAP, P@10, Recall@100)
                   --->  stage 6: calibration study (reliability diagram, ECE)
What makes this a research project rather than a tutorial
• Clef has never been evaluated on retrieval. Its published benchmarks are intent classification
and tool calling. There is no IR number for it anywhere. Whatever we measure is the first data point.
• We test whether its probabilities are calibrated against TREC's own graded relevance
judgments. Almost no re-ranking paper checks this; they report nDCG and stop.
• We hold the candidate set fixed across all four re-rankers, so any difference is attributable to the
re-ranker alone rather than to first-stage variation.
What we are not claiming
Pointwise LLM re-ranking by probability is not new — monoT5 scores documents by the softmax over 'true' /
'false' tokens, and UPR scores by query-regeneration likelihood. We say so explicitly in Section 6.
Overclaiming novelty is the fastest way to lose marks in a viva.

2  Background: the two problems
Why a standard zero-shot pipeline leaves quality unclaimed
Problem 1 — the query side: queries and documents do not look alike
Dense retrieval embeds the query and the document into one vector space and compares them. But the
two objects are structurally different. A TREC-COVID topic is a handful of words in interrogative form. A
relevant document is a long declarative abstract written in clinical vocabulary. Three specific failure
modes follow:

Problem 2 — the ranking side: first-stage scores are not relevance
Whatever the first stage returns, its scores are a proxy. They are not a judgment about whether the
document answers the question.

The structure of our answer
HyDE closes the first gap by making the query-side object look like a document. Clef closes the second by
having a model actually read the pair and return a probability. Because we measure the two stages
separately, we can say which one earned the improvement.

3  Stage A — HyDE query expansion
Method, prompt design, and parameters
The method in four steps
1
Generate. An instruction-tuned LLM is prompted to write a passage that would answer the query, in
the register of the target corpus. The passage may contain factual errors; this is accepted and
expected.
2
Encode. The generated passage, and the original query, are embedded with a contrastively trained
dense encoder (we use Contriever, matching the original paper).
3
Average. The N generated-passage embeddings and the query embedding are averaged into a
single dense vector.
4
Retrieve. That averaged vector drives nearest-neighbour search over the pre-encoded corpus index.
No training, no relevance labels, no feedback loop.
Why hallucination is survivable — and the answer to the obvious viva question
The dense encoder acts as a lossy compressor. It preserves what the generated passage is about — its
topic, its register, its domain vocabulary — and discards most of the specific invented detail, because
that detail is not what the embedding dimension budget is spent on. Averaging over N independent
generations further cancels idiosyncratic fabrications while reinforcing the signal common to all of them.
And in our pipeline there is a second safeguard the original paper does not have: Stage B re-reads every
candidate against the real document text, so a hallucination that survives into retrieval still has to pass a
relevance judgment.
Why HyDE rather than classical pseudo-relevance feedback
Classical PRF (Rocchio, RM3) runs the query, assumes the top-k results are relevant, harvests terms
from them, and re-runs. The weakness is structural: if the first retrieval is poor, you expand the
query with terms from irrelevant documents and make it worse. HyDE never touches the corpus
during expansion. The LLM writes from parametric knowledge, so expansion quality is independent of
retrieval quality. On a collection like TREC-COVID, where topics are short and clinical, that independence
matters.
Prompt specification
The prompt is frozen after week 3 and recorded here. Changing it invalidates every downstream run,
so a change is a decision-log entry and a full regeneration.

4  Stage B — Clef decision re-ranking
What Clef is, how it is called, and how we turn it into a ranker
What Clef is
Clef is a 27-billion-parameter decision model published by Cloudflare and distributed through Ollama
under the Apache 2.0 licence. Its model card states it is fine-tuned from a Qwen3-family 27B base.
Critically, it is not a text generator. You supply a state (text, structured JSON, or images) together
with between 1 and 64 typed questions, and it returns probabilities. That output shape is, almost
exactly, the shape of a relevance judgment — which is what makes it usable as a re-ranker at all.

Request shape

{
  "model": "clef",
  "state": "TOPIC: <query text>\n\nQUESTION: <topic question field>\n\n"
           "DOCUMENT TITLE: <title>\n\nDOCUMENT: <abstract text>",
  "questions": [
    {
      "name": "relevant",
      "type": "noul",
      "prompt": "The DOCUMENT is relevant to the TOPIC and helps answer the QUESTION."
    }
  ],
  "keep_alive": 0
}
-> response contains, per question name, the probability in [0, 1]
keep_alive is the VRAM lever
Setting keep_alive: 0 tells Ollama to unload the model as soon as the request completes. During a batch
run we leave it at the default so the model stays resident between the 5,000 calls; we set it to 0 on the final
call of a stage so the GPU is clear before the next stage loads a different model. See Section 15.
Turning probabilities into a ranking
For each of the 50 topics we hold a fixed list of 100 candidates from Stage A. For each (topic, candidate)
pair we issue one request and read the probability. The ranking is then simply a descending sort of those
100 probabilities. Ties are broken by the original Stage A rank, so the re-ranker can never do worse than
random on a tie. Every raw response is written to disk before sorting (Section 9), because the
probabilities themselves — not just the ordering — are the input to the calibration study in Section 14.

Why it counts
N1
First IR evaluation of Clef
Clef's published benchmarks are BANKING77, CLINC150, BFCL, API-Bank,
RouterBench and similar — intent classification, tool calling and routing. There
is no published retrieval number for this model. Whatever we measure is
the first data point, and that is true whether the result is positive or negative.
N2
Calibration of a
re-ranker's scores against
graded qrels
Re-ranking papers report nDCG and stop. We bin Clef's returned probabilities
and plot the observed relevance rate per bin against TREC's own judgments,
with expected calibration error. If P = 0.8 really corresponds to ~80% judged
relevant, a single threshold transfers across topics — a capability no score-based
re-ranker offers. This is our strongest and most distinctive figure.
N3
Purpose-built decision
model vs. coaxed token
probabilities
monoT5's probability is a by-product: you read logits from a model trained to
produce text. Clef was built to emit calibrated probabilities as its primary
interface. Whether that architectural difference yields better-calibrated
relevance scores is an open empirical question, and we answer it.
N4
Attributing the gain to a
stage
Most pipeline papers report one end-to-end number. We freeze the candidate set
and vary only the re-ranker across S4–S7, so the improvement from expansion
and the improvement from re-ranking are separately measurable.

493.5 relevant documents per topic changes how we read Recall
With that many relevant documents, Recall@100 is bounded very low by construction — retrieving 100
documents cannot recover 493. Do not report low Recall@100 as a failure. It is a property of the
collection. Recall@100 is in our table as a ceiling check: it tells us how much relevant material Stage A
handed to the re-ranker, and therefore bounds what any re-ranker could possibly achieve. nDCG@10 is the
metric that answers the research questions.
Published reference numbers — our correctness check
These are from the BEIR paper (Thakur et al., NeurIPS 2021 Datasets & Benchmarks). Reproducing the
BM25 row is the acceptance test for Stage 1 and Stage 3. If our BM25 does not land near 0.656,
something is wrong with the index, the qrels alignment, or the evaluation call — and we fix that before
generating a single hypothetical document.

The docids.json mapping is the highest-risk artefact in the project
FAISS returns row indices, not document IDs. If the order of corpus_emb.npy and docids.json ever
diverges, every run file silently points at the wrong documents and every metric becomes meaningless —
with no error raised. Write both in the same loop, in the same script, and never regenerate one without
the other. The Stage 1 acceptance check exists primarily to catch this.

11  Stage 1 to Stage 6 — the build
The full procedure. Each stage: what, how, output, acceptance check.
The golden rule of this pipeline
One model on the GPU at a time. Each stage loads what it needs, writes its output to disk, and exits. No
stage ever holds two models. This is what makes the project run on a single 32 GB card, and it is also what
makes every stage independently re-runnable.

Statistical significance
With 50 topics, an unlabelled difference in a table means very little. Every pairwise comparison we
report in the final document carries a significance marker.
• Test: two-sided paired Student's t-test over per-topic nDCG@10, which is what ranx.compare()

• Pairing: by topic — the same 50 topics run through both systems.
• Threshold: p < 0.05, with correction for multiple comparisons when the whole 7-system table is
compared at once.

never a bare bolded number.

For every topic, record whether each re-ranker helped or hurt relative to S3, and by how much. Then
pick the two or three topics with the largest losses and explain them: read the generated hypothetical
document, read the documents that were promoted, and say what went wrong. This is where the
analysis marks are. A results table anybody can produce; an explanation of why topic 23 broke is what
distinguishes the project.

14  The calibration study
Our distinctive contribution, in full detail
Why this section matters more than the results table
Any team can produce an nDCG table. Almost no re-ranking paper asks whether the scores mean anything.
Because Clef returns a probability rather than an arbitrary score, we can check it against TREC's own
judgments — and that check is the figure nobody else has for this model.
The question, stated precisely
When Clef says P(relevant) = 0.8 for a document, do roughly 80% of the documents it assigns 0.8 turn
out to be judged relevant by TREC's human assessors? If yes, the score is calibrated, and a single
relevance threshold transfers across topics — you can say “show everything above 0.7” instead of “show
the top 10”. No score-based re-ranker supports that, because a BM25 score of 18.4 or a cosine of 0.62
means something different on every query.
Procedure
1
Load clef_raw.jsonl (5,000 decisions) and the official qrels.
2
Join on (qid, docid). Handle unjudged documents explicitly: TREC pooling means many retrieved
documents were never assessed. Report the judged fraction, and run the analysis twice — once
treating unjudged as not-relevant, once excluding them. If the two tell different stories, that itself is a
finding worth a paragraph.
3
Binarise the ground truth for the main diagram: TREC grades 1 and 2 count as relevant, 0 as not
relevant. Record this choice; a 2-only variant is a reasonable robustness check.
4
Bin the predicted probabilities into 10 equal-width bins over [0, 1].
5
For each bin, compute the mean predicted probability and the observed fraction of relevant
documents. Plot observed against predicted, with the diagonal as the perfect-calibration reference.
This is the reliability diagram.
6
Compute expected calibration error (ECE): the bin-count-weighted mean absolute gap between
predicted and observed. Report Brier score alongside it.
7
Repeat for clef-flash and, if feasible, derive a comparable probability from the cross-encoder (a
sigmoid over its logit) so the diagram has a baseline curve.
8
Finally, the practical test: find the single threshold that maximises F1 across all topics, then report
how that fixed threshold performs per topic. Low variance across topics is the evidence that
calibration is useful rather than merely present.

You are not actually VRAM-constrained — but stage anyway
Clef at ~20 GB plus Qwen3-8B at ~6 GB would in fact fit in 32 GB. But the staged design is correct
independently of memory: it freezes the candidate set so the re-ranker comparison is unconfounded, it
makes any stage re-runnable alone, and it means a crash costs one stage rather than the run. We stage
because it is better science, and the GPU constraint is a convenient second reason.
Controlling residency
• Ollama loads models on demand and unloads idle ones automatically.
• keep_alive controls how long a model stays resident after a request. During a batch of 5,000 calls,
leave it at the default (or set "5m") so the model is not reloaded between calls — reloading per call
would dominate the runtime.
• Set keep_alive: 0 on the final call of a stage, so the GPU is clear before the next stage starts.
• Verify between stages with nvidia-smi and ollama ps. Never start a stage with a stale model
resident.

18  Viva preparation
The questions you will be asked, and the answers
Every team member should be able to answer all of these. The owner of each area should be able to go
two levels deeper on theirs.
Question
Answer
What is the project, in one
sentence?
One model imagines the document we are looking for so we can search with it; a
second model reads each candidate and returns a calibrated probability that it is
relevant.
What is actually new here?
Two things. Clef has never been evaluated on retrieval — its published
benchmarks are intent classification and tool calling — so our numbers are the
first. And we test whether its probabilities are calibrated against TREC's graded
judgments, which re-ranking papers essentially never do.
Isn't pointwise LLM re-ranking
already solved by monoT5?
Yes, and we say so. monoT5 reads the softmax over true/false tokens from a
generative model — the probability is a by-product. Clef was built to emit
calibrated probabilities as its primary interface. Whether that difference matters
empirically is our question, not our assumption.
What if the LLM hallucinates
the hypothetical document?
Three defences. The encoder is lossy — it keeps the topic and register and
discards most invented specifics. We average eight generations, which cancels
idiosyncratic fabrication. And Stage B re-reads the real document, so a
hallucination that survives into retrieval still has to pass a relevance judgment.
Why not just use a
cross-encoder?
We do — it is system S4, our baseline. The point is to measure whether a general
decision model, which never saw ranking supervision, is competitive with a model
trained on MS MARCO relevance data.
What happens if Clef loses?
That is hypothesis H3 and we expect it is possible. A supervised re-ranker beating
an unsupervised one is the boring outcome. The contribution is the measurement
plus the calibration finding, so a negative result is still a complete project with a
concrete diagnosis.
Why TREC-COVID rather than
another collection?
Graded 0/1/2 judgments, which we need to test the score question type and to
validate calibration; 50 topics; one-line load through BEIR; and published
reference numbers (BM25 = 0.656, BM25+CE = 0.757) that let us prove our
pipeline is correct before we draw any conclusion from it.
Why is your Recall@100 so
low?
TREC-COVID averages 493.5 relevant documents per topic. Retrieving 100 cannot
recover 493, so Recall@100 is bounded low by construction. We report it as a
ceiling on what the re-ranker could achieve, not as a quality score.
How do you know your BM25
implementation is right?
It reproduces the published BEIR figure of 0.656 nDCG@10. That check is a gate:
we did not generate a single hypothetical document before it passed, because it
validates the loader, the docid mapping and the evaluation call simultaneously.
Why should I believe a
difference of 0.02 nDCG@10?
You should not, unless it is significant. Every comparison we report carries a
two-sided paired t-test over the 50 topics with the p-value stated.
How does this run on one
GPU?
The pipeline is staged, with files on disk between stages, so only one model is
ever resident. That was partly a hardware constraint, but it is also what freezes
the candidate set so that S4 through S7 are a controlled comparison.
What would you do with more
time?
Three things: fuse the Clef probability with the BM25 score via reciprocal rank
fusion; test recalibration (Platt or isotonic) to see whether ordering and calibration
can be improved independently; and extend to a second collection to test whether
any finding transfers.

19  Glossary
Shared vocabulary — nobody should have to guess
Term
Meaning
BEIR
A benchmark bundling many IR test collections behind one loader, with qrels included. Our
access route to TREC-COVID.
Bi-encoder
Encodes query and document separately into vectors; fast, because documents can be
indexed in advance. Contriever is one.
Calibration
Whether a predicted probability matches the observed frequency. If documents scored 0.8 are
relevant ~80% of the time, the model is calibrated.
Candidate set
The top-k documents from the first stage that are handed to a re-ranker. Ours is frozen at 100
per topic.
Cross-encoder
Reads query and document together and outputs one relevance score. Accurate but slow, so it
is used only for re-ranking.
Decision model
A model whose output is a typed, calibrated probability rather than free text. Clef is one.
Dense retrieval
Retrieval by vector similarity in a learned embedding space, as opposed to lexical term
matching.
ECE
Expected calibration error — the bin-count-weighted mean gap between predicted probability
and observed frequency.
FAISS
A library for storing and searching dense vectors. We use flat inner-product (exact) search.
HyDE
Hypothetical Document Embeddings. Generate a passage that would answer the query,
embed it, and search with that.
Hole / unjudged
A retrieved document that no human assessor ever judged, because TREC pooling only judges
what the original participating systems returned.
nDCG@10
Normalised discounted cumulative gain at rank 10. Rewards placing highly relevant
documents near the top; uses graded judgments.
noul
Clef's yes/no question type, returning the probability a statement is true. Our primary ranking
signal.
Pointwise
re-ranking
Scoring each (query, document) pair independently, then sorting. Contrast with listwise, which
orders a whole set at once.
qrels
Query relevance judgments — the human-assessed ground truth, as (qid, docid, grade) triples.
Reliability
diagram
Predicted probability on the x-axis against observed relevance frequency on the y-axis. The
diagonal is perfect calibration.
Run file
A ranked result list in the standard six-column TREC format. The unit of evaluation.
Zero-shot
No training on the target collection's relevance data. Our whole pipeline is zero-shot.
